# Доступ к Larnitech MF-14.C в контуре «Офис»

## Назначение

Этот документ фиксирует фактически обнаруженные способы локального доступа к
контроллеру Larnitech MF-14.C без браузера. Он предназначен для повторного
использования в следующих сессиях и не является разрешением на изменение
реального оборудования.

## Проверенный узел

- Контур: клиент «Офис».
- Модель со слов пользователя: Larnitech MF-14.C.
- Локальный адрес: `192.168.1.185`.
- Панель настройки: LT Setup `4.150`.
- HTTP-сервер панели: Apache `2.4.54 (Raspbian)`.
- Дата сетевой проверки: 2026-09-20.

Адрес является внутренним адресом LAN, а не адресом внешнего доступа. Логины,
пароли, API-ключи, серийный номер, MAC-адрес и адреса исполнительных устройств
в репозитории не хранятся.

## Обнаруженные сервисы

| TCP-порт | Состояние | Назначение |
| --- | --- | --- |
| `22` | открыт | SSH; авторизация и команды не проверялись |
| `80` | открыт | LT Setup и внутренний HTTP RPC API |
| `2041` | открыт | официальный Larnitech API2 по WebSocket |
| `55555` | открыт | локальный/legacy-протокол приложений Larnitech; не исследовался |
| `502` | закрыт | Modbus TCP напрямую не обнаружен |
| `1883` | закрыт | MQTT напрямую не обнаружен |
| `8888` | закрыт | альтернативный API-порт не используется |

Дополнительно проверялись распространённые порты `21`, `23`, `53`, `81`,
`443`, `1900`, `4000`, `5000`, `8000`, `8080`, `8081`, `8443`, `8883` и
`10001`; открытых TCP-сервисов на них не обнаружено. Проверка UDP не
выполнялась.

## Рекомендуемый интерфейс: API2

Для чтения состояний, подписки на события и управления устройствами следует
использовать документированный API2:

```text
ws://192.168.1.185:2041/api
```

WebSocket handshake с этим адресом фактически завершился ответом
`101 Web Socket Protocol Handshake`. Авторизация и команды не выполнялись.

После установления соединения клиент авторизуется API-ключом из LT Setup:

```json
{"request":"authorize","key":"<API_KEY>"}
```

Основные документированные запросы:

```json
{"request":"get-devices","status":"detailed"}
{"request":"status-get","addr":"<DEVICE_ADDR>"}
{"request":"status-subscribe"}
```

Изменение состояния выполняется запросом `status-set`, но его нельзя посылать
в реальный контур без отдельного подтверждения пользователя и проверки типа
целевого устройства:

```json
{
  "request": "status-set",
  "addr": "<DEVICE_ADDR>",
  "status": {"state": "on"}
}
```

Поля `status` зависят от типа сущности. Нельзя считать `on/off` безопасным для
замков, ворот, клапанов, охраны, силовых нагрузок и других критичных функций.

Официальная документация:

- <https://wiki.larnitech.com/API2>
- <https://wiki.larnitech.com/Metaforsa2_MF-14/ru>

## Внутренний HTTP RPC LT Setup

Панель использует программный endpoint:

```text
POST http://192.168.1.185/api/api.php?api=<Namespace.method>
```

Это RPC, а не REST. Позиционные аргументы передаются как `param0`, `param1` и
далее. Сессия хранится в cookie `PHPSESSID`. Публичные read-only вызовы во
время проверки вернули:

- `Account.isLogged` — `data: false` без авторизации;
- `Account.getPanelVersion` — `LT Setup 4.150`;
- защищённые `Initialization.getDeviceStatus`, `JsModules.getModulesV2` и
  `AccessKeys.getWSData` — `result: false, data: false` без авторизации.

Клиентский код LT Setup показал следующий формат входа:

```bash
curl -c /path/outside-git/larnitech.cookies \
  --data-urlencode 'param0=<LOGIN>' \
  --data-urlencode 'param1=<PASSWORD>' \
  --data-urlencode 'param2=0' \
  'http://192.168.1.185/api/api.php?api=Account.login'
```

После входа сессионную cookie можно использовать для read-only RPC:

```bash
curl -b /path/outside-git/larnitech.cookies \
  -X POST \
  'http://192.168.1.185/api/api.php?api=AccessKeys.getWSData'
```

`AccessKeys.getWSData` используется самой панелью для получения параметров
WebSocket. В версии API2 клиент затем отправляет сообщение `authorize` с
выданным ключом.

Внутренний RPC не документирован как стабильный публичный контракт. Его можно
использовать для диагностики и автоматизации настроек только после фиксации
версии LT Setup, изучения конкретного метода и read-only проверки. Для обычной
интеграции предпочтителен API2.

## Безопасность

- На узле используются незашифрованные `HTTP` и `ws`; credentials и API-ключ
  нельзя передавать через недоверенную сеть.
- Не публиковать порты `22`, `80`, `2041` и `55555` в интернет. Для удалённого
  доступа использовать VPN или штатный защищённый механизм Larnitech.
- API-ключ, пароль и cookie хранить вне Git с правами доступа только владельцу.
- Перед автоматизацией сначала выполнить `get-devices`, затем read-only
  `status-get`/`status-subscribe` и составить обезличенную карту разрешённых
  сущностей.
- Для клиента управления использовать allowlist адресов и типов устройств;
  `status-set` по произвольному адресу запрещён.
- SSH открыт, но не является рекомендуемым прикладным API. Вход по SSH и
  изменение файлов контроллера в рамках проверки не выполнялись.

## Граница выполненной проверки

Проверка была только сетевой и read-only: TCP connect, публичные HTTP GET/RPC
запросы, чтение клиентского JavaScript и WebSocket handshake. Не выполнялись:

- авторизация в LT Setup или API2;
- получение списка устройств и их адресов;
- чтение показаний датчиков после авторизации;
- отправка `status-set`;
- изменение настроек, установка плагинов или вход по SSH;
- проверка поведения физического оборудования.

Поэтому подтверждена доступность интерфейсов, но не успешное управление
конкретными выходами или датчиками.
