# VAKIO как управляемое устройство Larnitech

## Цель

Сделать Larnitech единой точкой управления и состояния VAKIO Base Smart.
Raspberry Pi остаётся техническим адаптером API2 ↔ MQTT и не содержит
самостоятельной климатической политики.

## Подтверждённый интерфейс VAKIO

Прибор публикует и принимает локально три рабочих MQTT-топика:

- `vakio/state`: `on`, `off`;
- `vakio/workmode`: `inflow`, `inflow_max`, `recuperator`, `winter`,
  `outflow`, `outflow_max`, `night`;
- `vakio/speed`: целые значения `1`–`7`.

Системные команды обновления прошивки и сброса настроек в интерфейс Larnitech
не экспортируются: они не относятся к штатному управлению вентиляцией и могут
нарушить доступность или стереть конфигурацию.

## Представление в Larnitech

В отдельной области `VAKIO` создаются 15 виртуальных элементов типа `lamp`:

1. один выключатель питания;
2. семь взаимоисключающих селекторов режима;
3. семь взаимоисключающих селекторов скорости.

Такое представление намеренно многоканальное: каждый режим и каждая скорость
доступны обычным сценариям Larnitech без неоднозначного пересчёта процентов
диммера.

## Поток управления

1. Пользователь или сценарий включает виртуальный элемент Larnitech.
2. Gateway получает событие API2 только с заранее настроенного адреса.
3. Для режима или скорости gateway сначала гарантирует свежее подтверждение
   питания `on`, затем публикует выбранную MQTT-команду. Retained `state=on`
   не позволяет пропустить включение.
4. Команда считается выполненной только после совпадающего сообщения от VAKIO.
5. Gateway отражает подтверждённые `state`, `workmode` и `speed` обратно в
   виртуальные элементы Larnitech. Неактивные селекторы переводятся в `off`.
6. Команда, уже совпадающая с телеметрией VAKIO, повторно не отправляется.

Текущая ревизия Base Smart выполняет raw-команду выключения `06000`, но не
публикует после неё новое `state=off`; сохранённый MQTT-снимок остаётся
`state=on`. Для этой единственной команды gateway после успешной доставки
QoS1 фиксирует требуемое безопасное состояние `off` в retained-топике. Для
включения, режимов и скоростей по-прежнему требуется ответ прибора.

## Безопасность и отказ

- произвольные адреса API2 и произвольные MQTT payload запрещены;
- при устаревшей телеметрии новая команда не отправляется;
- при отсутствии подтверждения виртуальные элементы возвращаются к последнему
  фактически подтверждённому состоянию;
- при отказе Raspberry Pi сохраняется штатное ручное управление VAKIO, но
  виртуальные элементы Larnitech перестают обновляться;
- автоматизация по CO₂ в этом изменении не включается.

## Проверка

- модульные тесты всех 16 рабочих действий: питание `on/off`, семь режимов и
  семь скоростей;
- статическая компиляция Python;
- резервная копия Larnitech перед изменением `logic.xml`;
- повторное чтение XML и API2 inventory после сохранения;
- ограниченная проверка команд с обязательным MQTT-подтверждением и возвратом
  исходных состояния, режима и скорости.

Фактически выполнено: сохранение `logic.xml`, повторное чтение области `VAKIO`,
проверка 15 адресов в API2, 29 модульных тестов, статическая компиляция и
перезапуск gateway. После перезапуска MQTT и Larnitech имеют состояние
`online`, мост включён, прямое HTTP-управление выключено. Retained
`state=on` корректно оставляет VAKIO в `waiting` и не считается подтверждением
вращения вентилятора.

## Откат

1. Отключить `VAKIO_LARNITECH_BRIDGE_ENABLED` и перезапустить gateway.
2. Восстановить сделанную перед изменением ручную резервную копию Larnitech
   либо удалить только область `VAKIO` из `logic.xml`.
3. Проверить штатное локальное управление VAKIO.

## Критерии приёмки

- [x] В Larnitech видны питание, все семь режимов и все семь скоростей.
- [x] Каждый элемент доступен в сценариях Larnitech.
- [ ] Состояния Larnitech совпадают с подтверждённой MQTT-телеметрией.
- [ ] Неподтверждённая команда не остаётся отображённой как выполненная.
- [x] Сброс и обновление прошивки не экспортированы.
- [x] Сохранено штатное ручное управление VAKIO.
